# Техническое задание

**Изделие:** Mail Gateway — почтовый шлюз с HTTP-интерфейсом
**Версия:** 1.0
**Дата:** 20.07.2026
**Основание:** выделение почтовой подсистемы из проекта `somnium` в самостоятельный сервис

---

## 1. Назначение и цели

### 1.1. Назначение

Mail Gateway — самостоятельный сервис, обеспечивающий приём и отправку электронной почты
для одного или нескольких доменов. Прикладные системы работают с почтой исключительно
по HTTP API и не содержат кода работы с SMTP.

### 1.2. Решаемые проблемы

Почтовая подсистема `somnium` (`smtp_server.py`) на момент выделения имела следующие дефекты:

| № | Дефект | Последствие |
|---|---|---|
| 1 | Прямой импорт моделей монолита (`from models import db, Mail, User`) | Невозможно обновлять/перезапускать почту независимо; схема БД связана |
| 2 | Отправка синхронна внутри HTTP-запроса | При недоступности MX запрос висит до таймаута, письмо теряется без повтора |
| 3 | Нет очереди и повторных попыток | Разовый сетевой сбой = безвозвратно потерянное письмо |
| 4 | Уведомление о новом письме — POST без подписи, авторизации и повторов | Подделка событий; при рестарте потребителя события теряются |
| 3 | Пароль SMTP и API-токен в коде `config.py` | Компрометация при доступе к репозиторию |
| 4 | Приём письма целиком с последующим отказом «нет такого пользователя» | Бесполезный трафик и нагрузка |
| 5 | `sanitize_filename` сохраняла разделители пути в имени файла | Риск записи вложения за пределы каталога |
| 6 | HTML-часть письма преобразовывалась в текст и терялась | Невозможно корректно отобразить письмо в интерфейсе |
| 7 | Хост прослушивания задан константой `10.0.0.2` в коде | Перенос на другой сервер требует правки кода |

### 1.3. Цели

- Изолировать почтовую функциональность от прикладного кода.
- Обеспечить гарантированную обработку исходящих писем (очередь, повторы, журнал).
- Обеспечить доставку событий о входящих письмах с подтверждением и подписью.
- Дать возможность переиспользовать сервис в других проектах без изменения кода.

## 3. Требования к функциям

### 3.1. Приём входящей почты

| ID | Требование |
|---|---|
| F-01 | Сервис принимает соединения по SMTP на настраиваемых адресе и порту |
| F-02 | На стадии `RCPT TO` адрес получателя проверяется по реестру ящиков; неизвестный — `550 No such user here` без приёма тела |
| F-03 | Режим `MG_REQUIRE_KNOWN_MAILBOX=false` отключает проверку (приём всей почты домена) |
| F-04 | Из письма извлекаются: отправитель, получатель, тема, текстовая часть, HTML-часть, `Message-ID`, `In-Reply-To`, `References` |
| F-05 | При отсутствии `Message-ID` он генерируется в виде `<uuid4@домен>` |
| F-06 | Повторная доставка письма с известным `Message-ID` не создаёт дубликата и подтверждается кодом `250` |
| F-07 | Определяется ключ переписки `thread_key` — корневой `Message-ID` цепочки |
| F-08 | Вложения сохраняются в `<каталог>/<ящик>/<ГГГГ-ММ-ДД>/<id письма>/<имя>`; имя очищается от разделителей пути и служебных символов |
| F-09 | Вложение свыше `MG_MAX_ATTACHMENT_MB` пропускается с записью в журнал; письмо принимается |
| F-10 | При внутренней ошибке обработки возвращается `451`, чтобы отправитель повторил доставку |
| F-41 | Входящие соединения шифруются по STARTTLS при заданном сертификате; шифрование не требуется принудительно, иначе почта от серверов без TLS не дойдёт |
| F-42 | Проверяются SPF, DKIM и DMARC; результат сохраняется в письме и доступен через API |
| F-43 | Режим `MG_INBOUND_AUTH=enforce` отклоняет письмо с `550`, если домен отправителя заявил `p=reject`; `p=quarantine` и `p=none` — принимается с пометкой |
| F-44 | Сбой самой проверки (недоступен DNS) не приводит к потере письма: оно принимается непроверенным |
| F-45 | Размер письма ограничен `MG_MAX_MESSAGE_MB` и объявляется в `SIZE`; число писем с одного адреса — `MG_SMTP_RATE_LIMIT_PER_MINUTE` |
| F-46 | При `MG_PROXY_PROTOCOL=true` адрес отправителя берётся из заголовка PROXY protocol; без явного включения заголовок игнорируется |
| F-47 | Объявляется `SMTPUTF8` — адреса с не-ASCII символами принимаются |

### 3.2. Отправка исходящей почты

| ID | Требование |
|---|---|
| F-11 | Письмо ставится в очередь методом `POST /api/v1/messages`; ответ `202` с присвоенным `Message-ID` |
| F-12 | Домен отправителя обязан совпадать с `MG_DOMAIN`, иначе `422` |
| F-13 | Письмо без текстовой и без HTML-части отклоняется с `422` |
| F-14 | Вложения передаются идентификаторами файлов, предварительно загруженных через `POST /api/v1/uploads` |
| F-15 | Повторное использование уже прикреплённого файла отклоняется с `422` |
| F-16 | Фоновый воркер забирает письма из очереди и доставляет их вне HTTP-запроса |
| F-17 | Режим `direct`: разрешение MX-записей домена получателя, перебор серверов по приоритету, STARTTLS при поддержке |
| F-18 | Режим `relay`: отправка через внешний SMTP с аутентификацией и TLS |
| F-19 | При временной ошибке — повтор, до `MG_SEND_MAX_ATTEMPTS` раз, интервал `база × 2^(попытка−1)`, не выше `MG_SEND_RETRY_MAX_SECONDS`, с разбросом ±20% |
| F-20 | При постоянной ошибке (отказ получателя, отсутствие MX) повторы не выполняются, статус `failed` |
| F-21 | Текст последней ошибки сохраняется в письме и доступен через API |
| F-22 | При наличии `in_reply_to` формируются заголовки `In-Reply-To` и `References` |

### 3.3. Получение новых писем потребителем

Шлюз не инициирует соединений с потребителями. Единственный способ узнать о новой
почте — опросить API. Это осознанное решение: шлюз остаётся самостоятельным
модулем, которому не нужно знать ни адресов потребителей, ни их доступности.

| ID | Требование |
|---|---|
| F-23 | Потребитель получает новые письма запросом `GET /api/v1/messages?since_id=<курсор>` |
| F-24 | При заданном `since_id` выдача идёт по возрастанию `id`, чтобы ни одно письмо не проскочило мимо курсора при любом `limit` |
| F-25 | `since_id=0` означает «с самого начала»; отсутствие параметра — режим просмотра, выдача по убыванию |
| F-26 | Ответ содержит `total` — число записей за курсором, по нему потребитель решает, запрашивать ли следующую страницу немедленно |
| F-27 | `GET /api/v1/health` отдаёт `last_message_id` — стартовый курсор для потребителя, которому не нужна история |
| F-28 | Итог отправки доступен тем же способом: `direction=outgoing`, фильтр по `status`, поле `last_error` |
| F-29 | Каждое письмо имеет устойчивый `message_id` — потребитель может выстроить идемпотентную обработку при повторной выдаче |
| F-30 | Шлюз не выполняет исходящих HTTP-запросов и не хранит адресов потребителей |

### 3.4. Управление ящиками и чтение почты

| ID | Требование |
|---|---|
| F-31 | Регистрация/обновление ящика с привязкой `external_id` идемпотентным `PUT /mailboxes/{address}`; адрес нормализуется к нижнему регистру |
| F-32 | Список писем с фильтрами: направление, статус, ящик, получатель, только непрочитанные, `since_id`; постраничный вывод с общим числом записей |
| F-33 | Получение письма целиком, включая перечень вложений |
| F-34 | Отметка письма прочитанным через `PATCH /messages/{id}` |
| F-35 | Скачивание вложения по идентификатору с корректным `Content-Type` |
| F-36 | `GET /api/v1/health`: состояние сервиса, длины очередей, количество сбоев, опорный курсор |

### 3.5. Безопасность

| ID | Требование |
|---|---|
| F-37 | Все методы API, кроме `/ready`, требуют `Authorization: Bearer <токен>` |
| F-38 | Поддерживается несколько токенов (перечень через запятую) для раздельного отзыва |
| F-39 | Секреты задаются только переменными окружения либо файлом `.env`; в коде и репозитории отсутствуют |
| F-40 | Имена файлов вложений очищаются, запись вне назначенного каталога исключена |
| F-48 | Веб-панель `/admin`: вход по учётной записи, управление ящиками, смена пароля |
| F-49 | Пароли хранятся хешем `scrypt` со случайной солью; в открытом виде не хранятся и не журналируются |
| F-50 | Сессии серверные, cookie с `HttpOnly` и `SameSite=Strict`; выход завершает сессию на сервере |
| F-51 | Изменяющие формы защищены токеном CSRF, привязанным к сессии |
| F-52 | Попытки входа ограничены по адресу; неверные имя и пароль дают одинаковый ответ |
| F-53 | Учётные записи заводятся только из командной строки (`manage.py`), регистрации в панели нет |

### 3.6. Мультитенантность и лицензирование

| ID | Требование |
|---|---|
| F-54 | Данные разделены по клиентам: API-ключ принадлежит клиенту и видит только его домены, ящики, письма и вложения; чужая сущность отвечает `404`, не подтверждая существования |
| F-55 | API-ключи хранятся только хешем SHA-256; значение показывается один раз при выпуске в панели; отзыв — индивидуальный, отключение клиента отзывает все его ключи разом |
| F-56 | Домен глобально уникален и принадлежит одному клиенту; отправка и создание ящика возможны только на заранее зарегистрированном домене клиента (закрывает открытый релей и подлог отправителя между клиентами) |
| F-57 | DKIM настраивается по-доменно: свой ключ и селектор у каждого домена; замена файла ключа подхватывается без перезапуска; домен без ключа отправляет без подписи |
| F-58 | Лицензия — файл `license.lic` формата Somnium (RSA-2048-PSS/SHA-256); действующая лицензия обязательна для обработки почты: без неё приём по SMTP отвечает временным отказом `451`, очередь отправки встаёт (письма остаются `pending`), `POST /messages` отвечает `503`; действующая лицензия ограничивает число доменов полем `max_domains` |
| F-58.1 | Отсутствие лицензии не мешает работе программы: служба запускается и устанавливается, панель, настройки и просмотр переписки доступны — иначе лицензию некуда установить. Разрешение проверяется на каждом письме: установка `.lic` включает почту без перезапуска службы |
| F-59 | Токены из `MG_API_TOKENS` при старте идемпотентно превращаются в ключи клиента «Default» (совместимость и разработка); в бою ключи управляются панелью |

## 4. Нефункциональные требования

## 6. Порядок подключения потребителя

Шлюз — самостоятельный модуль и о потребителях ничего не знает. Подключение любой
системы сводится к четырём шагам и не требует изменений в шлюзе.

1. Развернуть шлюз. В панели (`/admin/clients`) создать клиента, зарегистрировать
   его домен и выпустить API-ключ — отдельный ключ на каждую интеграцию, тогда
   доступ отзывается по одному. (`MG_API_TOKENS` остаётся как удобство разработки:
   токены из неё превращаются в ключи клиента «Default».)
2. Зарегистрировать обслуживаемые адреса: `PUT /api/v1/mailboxes/{address}`, в
   `external_id` положить идентификатор сущности в своей системе. Он вернётся в
   каждом письме и избавит от сопоставления по адресу.
3. Отправку писем перевести на `POST /api/v1/messages`; вложения предварительно
   загружать через `POST /api/v1/uploads`.
4. Завести у себя хранение курсора и периодический опрос
   `GET /api/v1/messages?direction=incoming&since_id=<курсор>`. Курсор сохранять
   после обработки письма, обработку делать идемпотентной по `message_id`:
   тогда сбой потребителя приводит к повторной выдаче, а не к потере письма.

Исторические письма, если они есть во внешней системе, переносятся разовым скриптом
либо остаются на месте — шлюз используется только для новой почты.

## 7. Этапы работ

### Этап 1. Базовый шлюз — **выполнен**

Реализованы требования F-01…F-40, N-01…N-09. Комплект поставки:
исходный код, `.env.example`, README с описанием API, сквозной автотест `smoke_test.py`
(29 проверок, все проходят).

### Этап 1а. Приведение к промышленному уровню — **выполнен**

Рефакторинг по эталону `skil-good-app.md` и закрытие технического долга.

| № | Работа | Результат |
|---|---|---|
| 1а.1 | Разделение на слои: роут → сервис → модель | Роуты тонкие, бизнес-логика и SQL из них убраны |
| 1а.2 | Единая иерархия доменных ошибок и один обработчик | Ответ об ошибке одинаков для всех источников |
| 1а.3 | Единица работы (`get_db`): один commit на запрос | `commit()` из сервисов и роутов убран |
| 1а.4 | Загрузчики ресурсов `load_*` | Проверка «есть/нет» больше не копируется по роутам |
| 1а.5 | Общий каркас очереди `workers/base.py` | Повторы и backoff описаны один раз на обе очереди |
| 1а.6 | Единое файловое хранилище `services/storage.py` | Раскладка каталогов и очистка имён — в одном месте |
| 1а.7 | Версионирование схемы (Alembic) | Схема накатывается и обновляется, `create_all` убран |
| 1а.8 | Ограничение частоты обращений к API (было 2.4) | `MG_RATE_LIMIT_PER_MINUTE`, один механизм |
| 1а.9 | Журнал в stdout и файл с ротацией, JSON-режим, `request_id` | Требование N-08 закрыто полностью |
| 1а.11 | Возврат в очередь писем, застрявших в `sending` | Аварийная остановка больше не «подвешивает» письмо |
| 1а.12 | `/ready`, счётчики очередей в `/health` | Пригодность к работе за балансировщиком |
| 1а.13 | Модульные тесты (163) | Инварианты доступа, статусов и эффектов закреплены |
| 1а.14 | Ошибки по RFC 9457 (`application/problem+json`) | Отраслевой стандарт вместо самодельного конверта |
| 1а.15 | Ящик адресуется адресом, `PUT` вместо `POST`-upsert | Идемпотентность, не нужен предварительный запрос за `id` |
| 1а.16 | `PATCH /messages/{id}` вместо `POST /messages/{id}/read` | Ресурсная семантика вместо RPC-подобного действия |
| 1а.17 | `201 Created` + `Location`, `202` + `Location` | Клиент узнаёт адрес созданного ресурса из ответа |
| 1а.18 | Коллекции отдают страницу с `total` | По голому массиву нельзя понять, есть ли ещё записи |

## 8. Порядок приёмки

1. Развёртывание на площадке заказчика по инструкции README.
2. Успешный прогон `smoke_test.py` — все проверки пройдены.
3. Контрольный приём письма с внешнего адреса, событие получено внешней системой.
4. Контрольная отправка письма на внешний адрес, письмо доставлено во «Входящие»
   (для этапа 2 — с прохождением проверок SPF и DKIM).
5. Проверка повторов: при недоступном получателе письмо переходит в статус `failed`
   после исчерпания попыток, ошибка зафиксирована.
6. Подписание акта.

## 9. Ограничения текущей версии

Подлежат устранению на этапе 2 либо принимаются заказчиком осознанно:

- DKIM-подпись не формируется — доставляемость при прямой MX-отправке будет низкой;
- отчёты о недоставке не разбираются;
- один обслуживаемый домен на экземпляр сервиса;
- SQLite не рассчитан на несколько экземпляров шлюза одновременно — при горизонтальном
  масштабировании требуется PostgreSQL (захват задач воркерами уже реализован через
  `SELECT ... FOR UPDATE SKIP LOCKED` там, где СУБД это поддерживает).

### 9.1. Дефекты реализации, устранённые на этапе 1а

| № | Дефект | Последствие | Как устранено |
|---|---|---|---|
| 1 | SQLite при чтении терял метку часового пояса | `created_at` уходил в API без смещения; потребитель трактовал UTC как местное время | Тип `UTCDateTime`: нормализация в обе стороны для всех моделей |
| 2 | Письмо, застрявшее в статусе `sending`, не подхватывалось повторно | При аварийной остановке процесса письмо зависало навсегда | Возврат в очередь при старте, с учётом израсходованных попыток |
| 3 | Два вложения с одинаковым именем в одном письме | Второе затирало первое | Уникальный префикс в имени файла |
| 4 | Имена вида `CON`, `NUL`, `COM1` не отсекались | Под Windows это устройства, а не файлы: запись зависала или падала | Экранирование зарезервированных имён |
| 5 | Загружаемый файл целиком читался в память | Несколько параллельных загрузок по 25 МБ исчерпывали память | Потоковая запись с проверкой лимита по ходу |
| 6 | Токен сравнивался обычным `in` | Время ответа зависело от совпавшего префикса | `hmac.compare_digest` по всем токенам без ранних выходов |
| 7 | Тема письма принималась вместе с переводами строк | Позволяло дописать произвольные заголовки (`Bcc:` и др.) | Переводы строк вырезаются на границе |
| 8 | Загруженные, но не отправленные файлы не удалялись | Каталог вложений рос неограниченно | Плановая чистка по `MG_UPLOAD_TTL_HOURS` |
| 9 | Схема создавалась через `create_all` | На базе прошлой версии недостающие колонки не появлялись | Alembic как единственный источник схемы |
| 10 | Незамеченная небезопасная конфигурация (токен по умолчанию, несогласованные настройки релея) | Сервис молча работал в заведомо нерабочем или небезопасном режиме | Проверка связности настроек при старте, предупреждения в журнале |
