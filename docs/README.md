# Mail Gateway

Автономный почтовый движок: принимает входящую почту по SMTP, складывает её в собственную БД
и отдаёт наружу через HTTP API. Отправка писем — POST-запросом, получение новых —
опросом с курсором.

Самостоятельный сервис: ничего не знает о потребителях и никуда сам не ходит,
кроме почтовых серверов. Всё взаимодействие — через API.

## Запуск

```bat
copy .env.example .env
:: отредактируйте .env — минимум MG_DOMAIN и MG_API_TOKENS
run.bat
```

Или вручную:

```bat
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe run.py
```

Схема БД накатывается автоматически при старте (Alembic) — под межпроцессной
блокировкой (`schema.lock` рядом с базой): службу и окно программы запускают
одновременно, и без неё второй процесс падал на «table already exists». Интерактивная документация
API: `http://<host>:8025/docs`.

### Проверка

```bat
test.bat
```

Прогоняет модульные тесты (`pytest`, 163 проверки) и сквозной `smoke_test.py`,
который поднимает шлюз на временной БД, шлёт письмо по SMTP и дёргает API (29 проверок).

## API

Все методы, кроме `/ready`, требуют заголовок `Authorization: Bearer <ключ>`.

### Клиенты и ключи (мультитенантность)

Один инстанс обслуживает нескольких клиентов. У каждого клиента — свои
домены, ящики и API-ключи; всё это заводится в панели на странице
**Клиенты** (`/admin/clients`). Ключ выпускается сервером, показывается один
раз и хранится только в виде хеша SHA-256; отзывается индивидуально.

Ключ видит **только данные своего клиента**: списки ящиков и писем
фильтруются по владельцу, а чужой ящик, письмо или вложение по прямому
номеру отвечают `404` — как несуществующие, без подтверждения самого факта
их существования. Отправлять письма можно только с доменов своего клиента;
домен регистрируется в панели заранее (глобально уникален: один домен — один
владелец). Ящик создаётся только на зарегистрированном домене.

Переменная `MG_API_TOKENS` осталась как удобство разработки: при старте её
токены идемпотентно превращаются в ключи клиента «Default» с доменом
`MG_DOMAIN`. В бою ключи заводятся через панель, а переменную можно убрать.

DKIM теперь настраивается по-доменно: у каждого домена свой ключ и селектор
(страница клиента в панели; генерация — `python manage.py dkim-keygen
--domain имя`). Домен без ключа отправляет без подписи.

| Метод | Назначение | Ответ |
|---|---|---|
| `PUT /api/v1/mailboxes/{address}` | Привести ящик к заданному виду (идемпотентно) | `201` + `Location` при создании, иначе `200` |
| `GET /api/v1/mailboxes/{address}` | Ящик целиком | `200` |
| `GET /api/v1/mailboxes` | Страница ящиков (`limit`, `offset`) | `200` |
| `DELETE /api/v1/mailboxes/{address}` | Удалить ящик | `204` |
| `POST /api/v1/uploads` | Загрузить файл для вложения | `201` + `Location` |
| `POST /api/v1/messages` | Поставить письмо в очередь отправки | `202` + `Location` |
| `GET /api/v1/messages` | Страница писем (фильтры: `direction`, `status`, `mailbox`, `recipient`, `unread_only`, `search`, `since_id`, `limit`, `offset`) | `200` |
| `GET /api/v1/messages/{id}` | Письмо целиком | `200` |
| `PATCH /api/v1/messages/{id}` | Изменить письмо, например `{"is_read": true}` | `200` |
| `GET /api/v1/attachments/{id}` | Скачать вложение | `200` |
| `GET /api/v1/health` | Состояние, размеры очередей, число сбоев | `200` |
| `GET /api/v1/ready` | Готовность (для балансировщика), без токена | `200` |

Ящик адресуется своим почтовым адресом, а не числовым `id`: адрес уникален и
известен вызывающей стороне заранее, лишний запрос «узнать id» не нужен.
`POST /messages` отвечает `202`, а не `201`, потому что письмо принято, но ещё
не доставлено; итог появится по адресу из `Location`.

### Страницы коллекций

Коллекции возвращают не голый массив, а страницу — иначе клиент не может
отличить «записей больше нет» от «упёрлись в limit»:

```json
{"items": [ ... ], "total": 137, "limit": 50, "offset": 0}
```

### Формат ошибок — RFC 9457

Успех несёт код состояния, тело — само представление ресурса; конверта над ним нет.
Все ошибки — независимо от источника (доменная проверка, валидация схемы,
внутренний сбой) — приходят как Problem Details по RFC 9457:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json
```
```json
{"type": "/errors/validation-error",
 "title": "Данные не прошли проверку",
 "status": 422,
 "detail": "Отправитель должен быть в одном из доменов вашего клиента",
 "instance": "/api/v1/messages",
 "request_id": "3a1f60d3b343",
 "errors": {"sender": "домен не зарегистрирован за вашим клиентом"}}
```

- `type` — постоянный идентификатор вида проблемы, по нему клиент ветвится;
- `title` — название вида проблемы, одинаковое для всех её проявлений;
- `detail` — что произошло в этом конкретном случае;
- `instance` — путь запроса, `request_id` — тот же идентификатор, что и в журнале;
- `errors` и прочие расширения лежат верхним уровнем, как предписывает RFC.

Внутренности наружу не уходят: при ошибке 500 клиент получает только `request_id`,
стектрейс остаётся в журнале.

### Отправка письма

```bash
curl -X POST http://localhost:8025/api/v1/messages \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"sender":"sales@somnium.kz","recipient":"client@example.org",
       "subject":"Ваш заказ","body_text":"Здравствуйте!","external_id":"order-123"}'
```

Ответ `202`: `{"id": 17, "status": "queued", "message_id": "<...@somnium.kz>"}`.
Письмо уходит фоновым воркером; итог — в `GET /api/v1/messages/17` (`sent` или `failed` + `last_error`).

### Получение новых писем

Шлюз никого не уведомляет — потребитель сам спрашивает, что появилось. Он хранит
**курсор** (id последнего обработанного письма) и повторяет запрос:

```bash
curl -H "Authorization: Bearer $TOKEN"   "http://localhost:8025/api/v1/messages?direction=incoming&since_id=$CURSOR"
```

```json
{"items": [{"id": 43, "sender": "client@example.org", "subject": "Заявка", ...}],
 "total": 1, "limit": 50, "offset": 0}
```

Новый курсор — `id` последнего элемента `items`. Псевдокод потребителя:

```python
cursor = load_cursor()                      # 0 при первом запуске
while True:
    page = get(f"/api/v1/messages?direction=incoming&since_id={cursor}&limit=50")
    for message in page["items"]:
        handle(message)
        cursor = message["id"]
        save_cursor(cursor)                 # после обработки, а не до
    if page["total"] <= len(page["items"]):
        sleep(2)                            # догнали — можно подождать
```

Важные свойства протокола:

- **`since_id` переключает порядок на возрастающий.** Иначе `limit` отрезал бы
  старые письма, курсор прыгнул бы на самое новое, и пропущенные не вернулись бы
  уже никогда. Без `since_id` выдача идёт по убыванию — это режим просмотра, а не опроса.
- **`since_id=0` — законный курсор** «с самого начала»; отсутствие параметра и
  ноль означают разное.
- **`total` считает всё за курсором,** а не только текущую страницу: по нему видно,
  нужно ли сразу запрашивать следующую или можно подождать.
- **Курсор сохраняется после обработки.** Тогда падение потребителя приводит к
  повторной выдаче письма, а не к его потере; идемпотентность обработки — на стороне
  потребителя, `message_id` для этого и отдаётся.
- Стартовую точку «только новое, без истории» даёт `last_message_id` из `/health`.
- Все временные метки — в UTC с явным смещением (`+00:00`).

Результат отправки узнаётся так же: `GET /api/v1/messages?direction=outgoing&status=failed`
либо запрос конкретного письма по `Location` из ответа `202`.

## Устройство

Зависимости строго сверху вниз: роут → сервис → модель → БД.
Роут не содержит ни SQL, ни бизнес-ветвлений; сервис не знает про HTTP и
не вызывает `commit` — границей транзакции управляет зависимость `get_db`.

```
mail_gateway/
├─ app/
│  ├─ config.py          настройки из окружения с проверкой связности
│  ├─ constants.py       статусы, события, лимиты — без «магических строк»
│  ├─ db.py              движок, сессии, UTC-тип времени
│  ├─ models.py          модели + общее поведение очередей с повторами
│  ├─ schemas.py         формы запросов и ответов
│  ├─ logging_setup.py   журнал в stdout и файл, request_id, JSON-режим
│  ├─ schema_setup.py    накат миграций при старте
│  ├─ smtp_server.py     SMTP-транспорт (тонкий)
│  ├─ api/
│  │  ├─ errors.py       иерархия доменных ошибок
│  │  ├─ responses.py    Problem Details (RFC 9457) — единственное место
│  │  ├─ handlers.py     перевод исключения в HTTP — в одном месте
│  │  ├─ deps.py         единица работы, аутентификация, rate-limit
│  │  ├─ loaders.py      загрузка ресурса по идентификатору (бросает NotFound)
│  │  └─ routes/         роуты по доменам
│  ├─ services/          бизнес-логика: письма, ящики, приём, доставка
│  ├─ web/               панель управления: сессии, CSRF, шаблоны
│  └─ workers/           фоновые воркеры поверх общего каркаса очереди
├─ manage.py             служебные команды (учётные записи)
├─ check_inbound.py      диагностика приёма почты
├─ migrations/           версии схемы (Alembic)
├─ tests/                модульные тесты
└─ smoke_test.py         сквозная проверка
```

Очередь отправки обслуживается каркасом `workers/base.py`: захват задачи,
экспоненциальная пауза, исчерпание попыток и запись результата отделены от
самой доставки — в `OutboxWorker` остаётся только `handle()`.

## Эксплуатация

- **Служба Windows:** `service.py` (нужны права администратора):

  ```bat
  .venv\Scripts\python.exe service.py install
  .venv\Scripts\python.exe service.py start
  ```

  Запуск из `run.bat` живёт ровно до закрытия консоли и умирает вместе с
  сеансом RDP — для приёмника почты это не «сервис недоступен», а потерянные
  письма. Остановка службы идёт через тот же механизм, что и Ctrl+C: uvicorn
  доводит до конца текущие запросы и закрывает SMTP-слушатель, поэтому письмо,
  принятое, но ещё не записанное в базу, не пропадает после подтверждения
  отправителю.
- **Отчёты о недоставке:** входящее письмо вида
  `multipart/report; report-type=delivery-status` (RFC 3464) разбирается
  автоматически. Исходное письмо получает `bounced_at`, `bounce_status` и
  `bounce_diagnostic`; при постоянном отказе (код `5.x.x`) статус становится
  `bounced`. Временная помеха (`4.x.x`) статус не меняет — принимающая сторона
  ещё пытается доставить. Опознание строго по типу содержимого: угадывание по
  теме («Undelivered Mail…») пометило бы живую переписку как отказ.
- **Журнал:** stdout + `data/logs/mail_gateway.log` с суточной ротацией:
  текущий файл и `MG_LOG_RETENTION_DAYS` (по умолчанию 10) суточных архивов.
  Значок в трее пишет свой `data/logs/tray.log` с той же ротацией.
  `MG_LOG_JSON=true` переключает на JSON. В каждой строке — `request_id`.
- **Наблюдаемость:** `/health` (очереди, сбои, опорный курсор), `/ready` (БД и SMTP).
- **Миграции:** `alembic upgrade head` выполняется при старте; вручную —
  `.venv\Scripts\python.exe -m alembic upgrade head`.
- **Отправка:** `MG_SEND_CONCURRENCY` писем одновременно. Задача захватывается
  условным `UPDATE ... WHERE status = queued`, поэтому одно письмо не достаётся
  двум линиям обработки и не уходит получателю дважды.
- **Повторы:** пауза `база × 2^(попытка−1)`, но не выше
  `MG_SEND_RETRY_MAX_SECONDS` и с разбросом ±20% — иначе письма, отложенные
  одной аварией принимающей стороны, дозревают одновременно и обрушиваются на
  только что поднявшийся сервер единой пачкой.
- **Восстановление после сбоя:** письма, застрявшие в статусе `sending` после
  аварийной остановки, при следующем старте возвращаются в очередь.

  > Оговорка, которую стоит знать: если процесс упал *после* того, как
  > принимающий сервер подтвердил приём, но *до* записи статуса, письмо уйдёт
  > повторно. Отличить эти два случая нечем — SMTP не транзакционен. Выбор
  > сделан в пользу «лучше дважды, чем никогда»; при обратном приоритете
  > застрявшие письма надо не возвращать в очередь, а показывать оператору.
- **Чистка:** загруженные, но так и не отправленные файлы удаляются через
  `MG_UPLOAD_TTL_HOURS`.
- **Резервные копии:** снимок базы по расписанию, настраивается в панели
  (`/admin/backup`): включение, периодичность и предельный суммарный объём.
  При превышении лимита удаляются самые старые снимки; самый свежий не
  удаляется никогда, даже если он один больше лимита — смысл лимита в том,
  чтобы ограничить место, а не остаться вовсе без копий.

  Снимок делается через `VACUUM INTO`, а не копированием файла: база работает в
  режиме WAL, и обычная копия `.db` не содержит незавершённых транзакций из
  `-wal`, то есть теряет свежие письма — о чём узнаёшь только при
  восстановлении.

  **Вложения в снимок не входят намеренно.** Это файлы, которые пишутся один
  раз и больше не меняются; их копия в каждом снимке умножала бы объём без
  пользы. Синхронизируйте отдельно:
  `robocopy "data\attachments" "D:\резерв\attachments" /MIR`.
- **Восстановление:** остановить сервис, положить выбранный снимок на место
  `mail_gateway.db` (удалив `-wal` и `-shm`), вернуть каталог вложений, запустить.
- **Шифрование содержимого:** при заданном `MG_ENCRYPTION_KEY_FILE` тела писем
  (`body_text`, `body_html`, диагностика отказов) хранятся в базе зашифрованными
  (Fernet), а файлы вложений шифруются на диске. Ключ создаётся командой
  `python manage.py encryption-keygen`. Адреса и тема намеренно остаются
  открытыми — по ним работают поиск и фильтры. Записанное до включения ключа
  остаётся читаемым; новое пишется уже зашифрованным.

  **Ключ храните отдельно от резервных копий.** Снимок базы содержит только
  шифротекст: копия вместе с ключом обесценивает шифрование, копия без ключа
  при его утере невосстановима. Потеря ключа = потеря содержимого всех писем.

## Панель управления

`http://<хост>:8025/admin` — вход по учётной записи. Разделы:

- **Почта** (`/admin/messages`) — общий список входящих и исходящих с фильтрами
  по направлению, состоянию, ящику и подстроке в теме или адресе; в карточке
  письма видны заголовки, результат проверки подлинности, текст, HTML и вложения.
- **Написать** (`/admin/compose`) — отправка письма от имени любого активного
  ящика, с вложениями; кнопка «Ответить» в карточке подставляет адресата, тему
  и `In-Reply-To`. Письмо попадает в ту же очередь, что и отправленное через API.
- **Ящики** (`/admin/`) — добавление, изменение и удаление. Ящик создаётся
  только на домене, заранее зарегистрированном за клиентом, и автоматически
  принадлежит владельцу домена.
- **Клиенты** (`/admin/clients`) — клиенты, их домены (с настройкой DKIM
  по-доменно) и API-ключи: выпуск с одноразовым показом значения и отзыв.
  Отключение клиента мгновенно отзывает все его ключи, не удаляя данных.
- **Копии** (`/admin/backup`) — резервное копирование базы: включение,
  периодичность, предельный объём, снимок по кнопке, скачивание и удаление.
- **Лицензия** (`/admin/license`) — состояние лицензии и установка файла
  `.lic`. Действующая лицензия обязательна для работы (см. «Лицензия» ниже);
  она же ограничивает число доменов полем `max_domains`.
- **Сменить пароль** (`/admin/password`).

Первая учётная запись создаётся при первом запуске: если в базе нет ни одной,
`run.bat` спросит имя и пароль прямо в консоли, а GUI-режим (значок в трее,
в сборке — `MailGateway.exe` без аргументов) откроет мастер первоначальной
настройки и не продолжит работу без созданной записи. Под службой Windows
консоли нет — там вместо вопроса в журнал пишется, что выполнить `manage.py
create-admin` (в сборке — `MailGateway.exe create-admin`); приём почты от
наличия учётной записи не зависит и не блокируется.

## Значок в трее

`run.bat` вместе с сервером запускает значок в системном трее (`tray/`,
PySide6; отдельно — `.venv\Scripts\pythonw.exe -m tray.app`) — отдельный
лёгкий процесс, который **не** содержит сервера и секретов: состояние
читается из `GET /ready` (без токена) и диспетчера служб Windows. Меню
показывает состояние службы, API и лицензии, открывает панель и папку
журналов, диалог лицензии с установкой `.lic` и управляет службой
(пуск/стоп/перезапуск). Управление службой требует прав администратора,
а программа живёт в автозагрузке пользователя и запускается без них —
недостающие права запрашиваются через UAC на месте: тот же exe
перезапускается с одной командой (`start`), делает своё дело и завершается.
Постоянно работать с правами администратора незачем, а автозагрузка с ними и
вовсе не работает. Закрытие значка на почту не влияет.

Программа запускается **в единственном экземпляре** (именованный мьютекс
сеанса): второй запуск показывает, где искать значок, и выходит. Иначе в трее
набирался десяток одинаковых значков, каждый со своим опросом службы.

Без действующей лицензии значок сразу открывает диалог установки `.lic` —
почта в таком состоянии не обрабатывается, и оператор должен узнать об этом
сразу, а не по молчащей очереди.

Как панель обращается с чужим содержимым:

- **HTML-тело письма никогда не попадает в разметку панели.** Его пишет
  отправитель, то есть кто угодно из интернета, и один `<script>` внутри дал бы
  доступ к сессии администратора. Тело отдаётся отдельным документом и
  подключается через `<iframe sandbox>` — без `allow-scripts` и
  `allow-same-origin`, со своей политикой `default-src 'none'`.
- **Внешние загрузки внутри письма заблокированы.** Иначе картинка-маячок
  подтверждала бы отправителю, что письмо прочитали.
- **Вложения отдаются только на скачивание** (`application/octet-stream`,
  `Content-Disposition: attachment`). Вложенный HTML или SVG, открытый браузером
  с нашего происхождения, — это тот же XSS.

Учётные записи заводятся из командной строки, регистрации в панели нет:

```bat
.venv\Scripts\python.exe manage.py create-admin admin
.venv\Scripts\python.exe manage.py list-admins
.venv\Scripts\python.exe manage.py set-password admin
```

Пароль спрашивается интерактивно и не отображается при вводе — аргументом
командной строки его передавать не следует, он попадёт в историю и в список
процессов.

Как устроен доступ:

- пароли хранятся хешем `scrypt` со случайной солью, в открытом виде нигде;
- сессии живут на сервере, наружу уходит только случайный идентификатор в
  cookie с `HttpOnly` и `SameSite=Strict`; выход завершает сессию на сервере;
- каждая изменяющая форма несёт токен CSRF, привязанный к сессии;
- попытки входа ограничены `MG_WEB_LOGIN_ATTEMPTS_PER_MINUTE` на адрес;
- «неверное имя» и «неверный пароль» дают одинаковый ответ — иначе перебором
  выясняется список существующих учётных записей.

> **Порт 8025 не следует публиковать в интернет как есть.** По открытому HTTP
> cookie сессии перехватывается вместе с доступом в панель. Либо держите порт
> только в локальной сети, либо публикуйте через HTTPS-прокси (вот здесь Nginx
> Proxy Manager как раз уместен — это обычный HTTP) и ставьте
> `MG_WEB_SECURE_COOKIES=true`.

Панель можно выключить целиком: `MG_WEB_ENABLED=false`.

## Лицензия

Почта ходит только с действующим файлом `license.lic` в корне развёртывания
(рядом с `.env`) — форма Somnium: JSON с подписью RSA-2048-PSS/SHA-256,
проверяемой встроенным открытым ключом. Подделать файл без закрытого ключа
нельзя: правка любого поля ломает подпись, чужая лицензия отбраковывается по
`program_id`, а переведённые назад часы — по дате выдачи.

Лицензия нужна **почте, а не запуску**. Служба поднимается всегда — иначе
лицензию было бы некуда установить, а оператор видел бы остановленную службу
и требование прав администратора. Без действующего файла:

- **приём по SMTP отвечает временным отказом** (`451`) на команде `MAIL
  FROM`, то есть тело письма даже не принимается по сети. Именно временный
  код: отправитель повторяет доставку несколько дней, и письма дойдут после
  установки лицензии, а не вернутся авторам как несуществующим адресатам;
- **исходящая очередь встаёт.** Воркер отправки уходит на паузу, письма
  остаются `pending` и уйдут сами. Помечать их `failed` было бы потерей
  чужой почты из-за нашей коммерции;
- **`POST /api/v1/messages` отвечает `503`** с объяснением: письмо, молча
  осевшее в очереди навсегда, интегрирующая система считает отправленным;
- **всё остальное работает** — панель, настройки, просмотр переписки,
  служебные команды. Через панель (`/admin/license`) или значок в трее
  лицензия и устанавливается.

Разрешение спрашивается **на каждом письме**, а не однократно при старте:
положенный в работающий шлюз файл включает почту сам, без перезапуска службы,
и так же сам выключает её по окончании срока. Это дёшево — файл
перечитывается только при смене времени изменения и не чаще раза в минуту.

Действующая лицензия ограничивает число зарегистрированных доменов полем
`max_domains`. Количество писем, ящиков и обращений к API не ограничивается.
О приближении конца срока предупреждают за 30 дней — журнал, панель и трей.
Получить или продлить: <https://somnium.kz/licensing>.

## Сборка поставляемого каталога

`python build.py` собирает `dist/MailGateway` (PyInstaller, onedir) с одним
`MailGateway.exe` на все режимы (точка входа `mailgateway.py`):

- **без аргументов** — GUI: значок в трее. Если в базе нет ни одной учётной
  записи панели, сначала открывается мастер первоначальной настройки
  (`tray/setup_dialog.py`) — без создания администратора программа не
  запустится; затем показывается заставка (`tray/welcome_overlay.py`),
  гаснущая после первого опроса состояния службы. Тот же запуск без
  аргументов из диспетчера служб — работа службой: процесс сам определяет,
  кто его поднял (ошибка 1063 диспетчера = запуск человеком).
- `install` / `start` / `stop` / `restart` / `remove` — управление службой
  Windows (`service.py`); `debug` — запуск сервера прямо в текущей консоли,
  без службы.
- `create-admin` / `set-password` / `list-admins` / `dkim-keygen` /
  `encryption-keygen` / `dns-records` — служебные команды (`manage.py`), для
  скриптов и автоматизации: интерактивно администратора создаёт мастер.

Exe собран без консоли; консольные команды сами подключаются к консоли, из
которой их вызвали (`AttachConsole`), так что вывод `install` или
`create-admin` виден в том же окне cmd.

После компиляции `build.py` шифрует шаблоны панели: каждый `.html` в сборке
превращается в `.enc` (Fernet, ключ обфусцирован в `encryption_key.dat`
рядом), оригинал удаляется; на лету их расшифровывает
`app/web/encrypted_loader.py`. Это защита внешнего вида продукта от правки в
поставленной копии, не криптография. В дев-режиме `.enc`-файлов нет и панель
работает по обычным `.html`.

В сборку намеренно не входят `.env`, `license.lic`, `data/` и БД — они живут
рядом с exe (см. `BASE_DIR`): апдейт сборки заменяет каталог целиком, не
трогая операторские файлы. Рядом кладётся `.env.example` как заготовка.

Графическая часть (значок в трее, мастер первого запуска, заставка) построена на
**PySide6**, а не на PyQt5: PyQt5 распространяется под GPL v3 и в
проприетарной поставке обязывал бы открыть исходный код продукта целиком.
PySide6 — LGPL, и при динамическом подключении Qt (в сборке `Qt6*.dll` лежат
рядом с exe) закрытая поставка допустима. В `mail_gateway.spec` чужие
привязки к Qt (`PyQt5`, `PyQt6`, `PySide2`) занесены в `excludes`: случайно
оставшийся в окружении пакет иначе попал бы в сборку и вернул бы GPL-код в
поставку.

### Установщик (Inno Setup)

Последним шагом `build.py` собирает `dist/MailGateway-Setup-<версия>.exe` —
если в системе найден `ISCC.exe` (Inno Setup 6.3 и новее; проверено на 7). Не найден — шаг пропускается
с подсказкой, каталог сборки от этого не страдает; собрать вручную:
`ISCC.exe installer\mail_gateway.iss`. Отключить шаг целиком:
`build.py --no-installer`.

Что делает установщик:

- показывает **лицензионное соглашение** (`installer/LICENSE.txt`) и кладёт
  его копию в каталог программы;
- **спрашивает файл `.lic`** отдельной страницей мастера и копирует его до
  первого запуска службы. Файла ещё нет — страницу можно пропустить: служба
  всё равно установится и запустится, просто не будет обрабатывать почту,
  пока лицензию не поставят через значок в трее или панель;
- регистрирует **службу** с автозапуском (`sc config start= auto`) и
  перезапуском после сбоя; при обновлении поверх рабочей копии сначала
  останавливает её (`net stop`), иначе файлы сборки заняты;
- по желанию открывает порты в **брандмауэре**: SMTP 25 — отмечено, HTTP API
  8025 — нет (публиковать панель в интернет как есть не следует, см. выше);
- кладёт ярлык на **рабочий стол** и, по желанию, в **автозагрузку** (для
  всех пользователей: установщик работает от администратора, и ярлык в его
  личной автозагрузке не появился бы у оператора);
- при удалении снимает службу и правила брандмауэра, но **не трогает данные**:
  `.env`, `license.lic`, `mail_gateway.db` и `data/` остаются в каталоге.

Каталог установки по умолчанию — `C:\MailGateway`, а не Program Files:
операторские файлы живут рядом с exe, и программа, запущенная от обычной
учётной записи, в Program Files не смогла бы записать ни лицензию, ни
настройки.

Текст соглашения и `installer/version.iss` **создаются**
`installer/make_license.py` из `app/__init__.py` (версия) и
`docs/generate/config.py` (реквизиты ИП) — того же файла, откуда их берут
коммерческое предложение и инструкция. Править сгенерированные файлы руками
бессмысленно: следующая сборка их перепишет. Незаполненные реквизиты
генератор называет вслух — перед сборкой для заказчика заполните `EXECUTOR`
в `docs/generate/config.py`.

## Безопасность приёма

### Шифрование (STARTTLS)

Задайте `MG_TLS_CERT_FILE` и `MG_TLS_KEY_FILE` — шлюз объявит STARTTLS и будет
шифровать входящие соединения. Требовать шифрование нельзя: публичный MX обязан
принимать почту и от серверов без TLS, иначе письма просто не дойдут.

**Порт 25 нельзя проксировать через HTTPS-терминатор.** В SMTP шифрование
включается командой `STARTTLS` посреди уже открытого текстового соединения, а не
оборачивает его с первого байта, как в HTTPS. Если Nginx Proxy Manager или
аналогичный прокси терминирует TLS на 25-м порту, отправитель пошлёт `EHLO`
открытым текстом, получит рукопожатие TLS и оборвёт соединение. Порт 25
пробрасывается сквозным TCP, сертификат отдаётся шлюзу.

### Записи DNS для своего домена

Без правильных записей почта либо не приходит, либо уходит в спам, и понять
это по журналу нельзя. Программа сама показывает весь нужный набор:

```bat
MailGateway.exe dns-records                 что добавить
MailGateway.exe dns-records --check         и что из этого уже настроено
MailGateway.exe dns-records --domain a.kz   для домена клиента
```

Тот же список — в окне программы: **«Настройки» → «Записи DNS»**, с кнопками
копирования и проверкой. Мастер первого запуска кладёт его же в
`dns_record.txt` рядом с программой.

| Запись | Что делает | Без неё |
|---|---|---|
| `A` на `mail.<домен>` | адрес сервера, он же имя в HELO | почта не придёт |
| `MX` на `@` | куда приносить письма домена | почта не придёт |
| `TXT` (SPF) на `@` | кому можно писать от имени домена | письма в спам |
| `TXT` (DKIM) на `<селектор>._domainkey` | открытый ключ подписи | письма в спам |
| `TXT` (DMARC) на `_dmarc` | что делать при непрохождении проверок | письма в спам |
| `PTR` для IP-адреса | обратное имя сервера | письма отбиваются |

Две вещи, на которых спотыкаются чаще всего:

- **Поле «Хост» в панели регистратора — имя относительно зоны.** Вписывать
  `mail._domainkey`, а не `mail._domainkey.example.kz`: панель допишет зону
  сама, иначе получится `mail._domainkey.example.kz.example.kz`. Ориентир —
  как показаны уже существующие записи в той же зоне.
- **`mail` в `mail._domainkey` — это селектор DKIM** (`MG_DKIM_SELECTOR`), а
  не имя хоста. С записью `mail.<домен>` он не конфликтует и живёт в зоне
  рядом с ней; при селекторе `s1` запись звалась бы `s1._domainkey.<домен>`.

**PTR ставится не в зоне домена**, а владельцем IP-адреса — заявкой
провайдеру или хостингу. Крупные почтовые службы отвергают письма, у которых
обратное имя не совпадает с HELO; типовой адрес провайдера вида
`client.fttb.example.net` читается как «домашний интернет» и почти
гарантирует спам-папку. Проверка `--check` это показывает.

**DMARC начинать с `p=none`.** Это «ничего не делать, только присылать
отчёты»: политика ужесточается до `quarantine` и `reject` после того, как в
отчётах перестанут появляться собственные письма.

### Подлинность отправителя (SPF, DKIM, DMARC)

Речь ниже — о проверке **входящих**: чужие письма проверяются теми же
механизмами, что и наши на чужой стороне.

Без проверок шлюз примет письмо, в поле `From` которого написано что угодно.
Результат каждой проверки сохраняется в письме и виден через API:

```json
{"id": 43, "sender": "client@example.org",
 "spf_result": "pass", "dkim_result": "pass", "dmarc_result": "pass"}
```

Решение о доверии принимает потребитель — можно отбирать подозрительные письма
запросом `GET /api/v1/messages?dmarc_result=fail`.

Режим задаётся `MG_INBOUND_AUTH`:

| Значение | Поведение |
|---|---|
| `off` | не проверять (экономит DNS-запросы) |
| `annotate` | проверить, записать результат, принять всё — **по умолчанию** |
| `enforce` | отклонить с `550`, если домен отправителя сам требует этого (DMARC `p=reject`) |

Начинать следует с `annotate` и посмотреть в журнале, что начало бы отбиваться;
переключать в `enforce` — после этого. Своей политики поверх чужой шлюз не
выдумывает: `p=quarantine` и `p=none` означают «решай сам», и письмо принимается
с пометкой.

### Адрес отправителя за прокси

SPF проверяет **IP того, кто подключился**. Если перед шлюзом стоит прокси,
шлюз видит адрес прокси, и SPF перестаёт работать для всех писем сразу.

- **Прямой проброс порта (DNAT)** — исходный адрес сохраняется, ничего настраивать
  не нужно, `MG_PROXY_PROTOCOL=false`. Рекомендуемый вариант.
- **PROXY protocol** — если прокси убрать нельзя: включите `proxy_protocol on;`
  в его stream-секции и `MG_PROXY_PROTOCOL=true` в шлюзе.

`MG_PROXY_PROTOCOL=true` без доверенного прокси перед шлюзом — дыра: любой
подключившийся сможет объявить себя чужим адресом и пройти SPF. Поэтому по
умолчанию заголовок игнорируется.

### Лимиты

`MG_MAX_MESSAGE_MB` ограничивает письмо целиком на уровне SMTP (объявляется в
`SIZE`), `MG_SMTP_RATE_LIMIT_PER_MINUTE` — число писем с одного адреса.
Число SMTP-команд на соединение ограничено, `SMTPUTF8` включён — адреса с
кириллицей принимаются.

## Развёртывание в бой

Отправка напрямую по MX (`MG_OUTBOUND_MODE=direct`) требует, чтобы письма принимали чужие
почтовые системы. Без этого письма будут уходить в спам или отбиваться:

1. **Порт 25 наружу.** У большинства облачных провайдеров закрыт по умолчанию — запросить открытие.
2. **PTR-запись** IP → `mail.somnium.kz`, настраивается у хостера.
3. **SPF:** `v=spf1 ip4:<ваш IP> -all` в TXT-записи домена.
4. **DKIM:** создать ключ и получить запись для DNS —
   `.venv\Scripts\python.exe manage.py dkim-keygen`. Команда печатает готовую
   TXT-запись `<селектор>._domainkey.<домен>` и закрывает файл ключа от чужих
   учётных записей. Подпись включается сама, как только задан
   `MG_DKIM_PRIVATE_KEY_FILE`.
5. **DMARC:** `v=DMARC1; p=none; rua=mailto:postmaster@somnium.kz`.
6. **MX** домена → на хост шлюза.

Альтернатива без всей этой возни — `MG_OUTBOUND_MODE=relay` через внешний SMTP
(Mailgun, SendGrid, Яндекс 360, почта хостера): доставляемость их забота, шлюз только ставит в очередь.

Шлюз не является открытым релеем: домен отправителя обязан совпадать с `MG_DOMAIN`,
а частота обращений к API ограничена `MG_RATE_LIMIT_PER_MINUTE`.

### Шифрование исходящего канала

Два режима требуют прямо противоположного, и в коде это разные контексты TLS:

- **Релей — с проверкой сертификата** (`MG_RELAY_VERIFY_TLS=true`). По этому
  каналу уходят логин и пароль; без проверки любой, кто способен вклиниться в
  соединение, предъявляет собственный сертификат и получает право рассылать
  почту от имени домена. Если сервер не поднял STARTTLS, а `MG_RELAY_USE_TLS=true`,
  учётные данные не отправляются вовсе — письмо уходит в `failed`.
- **Прямая доставка на чужой MX — без проверки**, намеренно (RFC 7435).
  У публичных MX сплошь и рядом самоподписанные сертификаты и имена, не
  совпадающие с MX-записью. Требование проверки не дало бы защиты, а превратило
  бы доставку в отказ: альтернатива на 25-м порту — открытый текст, который
  отправитель обязан принять.
